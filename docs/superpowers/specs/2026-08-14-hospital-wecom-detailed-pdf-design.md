# 建始民族医院企业微信详细报告导出设计

## 目标

医院版问卷提交成功后，在现有企业微信摘要消息之后自动发送一份可直接下载的客户版 PDF 详细报告。报告用于院内健康管理人员快速阅读和后续沟通，不作为疾病诊断、男性衰老总分或生物年龄结论。

完整逐题答案、具体医学安全答案和内部触发规则继续保留在数据库及受鉴权保护的 `adminSurvey` 数据通道，不作为企业微信群文件或公开下载链接传播。

## 已选方案

采用“单次提交、两条群消息、一个受保护详情源”的结构：

1. 现有彩色 Markdown 摘要先发送，便于工作人员快速判断跟进优先级。
2. 云函数在内存中生成客户版 PDF，通过同一个企业微信机器人上传文件并发送到目标群。
3. 原始答案和院内专业详情继续由现有 `adminSurvey` 鉴权接口按记录编号读取，不生成公开链接。

未采用的方案：

- 把全部内容拼成一条 Markdown：受 4096 字节限制，手机端难以阅读，也不适合多页图表。
- 使用第三方 HTML/PDF 服务：会引入额外健康数据出境面和服务依赖。
- 把专业版 PDF 直接放进群：会扩大性健康、情绪、自伤及用药等敏感信息的传播范围。

## 报告内容

PDF 使用 A4 竖版、鲜明但克制的医疗健康视觉体系，包含：

1. 品牌与记录信息：医院名称、报告名称、姓名、手机号、记录编号、提交时间。
2. 核心诉求：最多三个主要问题、最近半年最明显变化、首要改善目标。
3. 八维功能状态画像：每个维度显示状态标签、触发线索和建议；红旗时统一显示“需医务人员优先核实”，不展示具体红旗答案。
4. 状态分布图：使用三段横向状态条与精确数量，展示“建议评估 / 变化信号 / 基本稳定”，不计算百分比、总分或身体年龄。
5. 生活方式概览：工作状态、久坐、运动、力量训练、饮酒、吸烟、晚间进食和饮食结构等结构化选项。
6. 12 周目标：客户愿意开始的改变和首要改善目标。
7. 边界说明：问卷不是诊断工具，正式评估需结合体检、实验室、既往资料及专项检测。

报告不包含：逐题分值表、具体红旗答案、内部触发规则全文、疾病诊断、未经验证的健康总分和生物年龄。

## 视觉体系

- 页面：A4 竖版，统一页眉、页脚和页码。
- 主色：深海军蓝；辅色使用亮蓝、青绿、橙红和中性灰。
- 图形：状态胶囊、八维卡片、三段状态条、编号圆点和分区色带。
- 字体：随云函数部署开源中文字体，确保 Linux 云端和本地渲染一致。
- 可读性：正文不小于 9.5pt，避免内容溢出、黑方块、重叠和跨页断裂。

## 组件边界

### `report-model.ts`

纯函数把 `PersistedSubmission` 转为安全的 `HospitalClientReportModel`。所有选项通过医院问卷定义映射；未知值显示“未填写”，不得回显未验证输入。该层负责隐私边界和医学表达，不负责绘制。

### `report-pdf.ts`

只接受 `HospitalClientReportModel` 和字体路径，返回 `Promise<Buffer>`。使用 PDFKit 绘制文本、状态卡片和图表，不访问数据库、网络或环境变量。

### `wecom.ts`

增加两个网络动作：

- `uploadWeComFile(webhookUrl, filename, pdfBuffer)`：从已校验 Webhook 中读取机器人 key，调用 `/cgi-bin/webhook/upload_media`，返回 `media_id`。
- `sendWeComFile(webhookUrl, mediaId)`：调用原发送入口发送 `msgtype=file`。

两个动作都设置 5 秒超时，校验 HTTP 状态和企业微信 `errcode`，错误信息不包含 Webhook key。

### `index.ts`

医院摘要发送成功后生成并发送 PDF。摘要和 PDF 分别写审计：

- `hospital_wecom_notification`
- `hospital_wecom_report_notification`

PDF失败不回滚已经成功保存的问卷，也不影响摘要消息；诺玛元一通知行为保持不变。

## 数据流

```text
医院问卷提交
  -> 身份/答案/评估分表入库
  -> 发送彩色摘要
  -> 构建安全报告模型
  -> 生成 PDF Buffer
  -> 企业微信上传文件得到 media_id
  -> 企业微信群发送 PDF
  -> 写入独立报告通知审计
```

## 文件名与幂等性

文件名格式为 `建始民族医院_健康评估报告_<安全姓名>_<记录编号>.pdf`。姓名只保留适合文件名的中文、字母、数字、空格、下划线和连字符，最长 24 个字符。

问卷提交仍以 `clientSubmissionId` 幂等。只有首次成功入库执行通知；重复请求返回已有结果，不重复推送摘要或 PDF。

## 错误处理

- 未配置医院 Webhook：摘要和 PDF 均记录 `not_configured`。
- 摘要失败：仍尝试生成并发送 PDF，以避免单一消息类型故障阻断详细报告。
- PDF生成失败、上传失败或文件消息失败：报告审计记录 `failed`，问卷提交仍返回成功。
- 报告模型发现未知选项：使用“未填写”，不得把原值注入 PDF。
- 医学安全红旗：报告只显示统一安全提示，不输出题号、答案或症状细节。

## 测试与验收

1. 报告模型单元测试覆盖正常记录、未知选项、红旗脱敏和生活方式映射。
2. PDF测试确认 `%PDF` 文件头、至少两页、核心字段存在于模型并完成生成；视觉验收使用 Poppler 渲染所有页面为 PNG。
3. 企业微信测试覆盖上传 URL、multipart 文件名、`media_id`、文件消息和错误脱敏。
4. 通知编排测试确认医院版产生独立报告审计，诺玛元一不发送医院 PDF。
5. 全量执行测试、类型检查、双品牌构建、云函数构建和生产依赖安全审计。
6. 部署后使用明确标注的虚构客户提交，确认两个企业微信审计均为 `sent`，再按唯一会话 ID 清理五个集合中的测试记录。

## 自审结论

- 无待定项或占位符。
- PDF群附件与受保护专业详情的隐私边界一致。
- 报告内容不引入诊断、总分或身体年龄。
- 组件接口、失败隔离和审计动作均有明确归属。
- 本次范围不新增管理端页面或公开报告链接，避免把已受保护的数据重新暴露到 URL。
