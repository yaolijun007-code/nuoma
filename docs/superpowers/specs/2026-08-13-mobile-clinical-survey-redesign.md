# 建始民族医院男性健康问卷移动端重构设计

## 目标

在不破坏现有 CloudBase 数据库、评估规则、幂等提交、管理接口和诺玛元一独立构建的前提下，将医院版问卷重构为“一页一题”的正式移动端健康采集入口。主要适配微信、企业微信和手机浏览器的 375px、390px、393px、430px 宽度，桌面端以 480px 内容列居中展示。

## 已审查现状

- `App.tsx` 以 section 为导航单位，每页同时渲染多题，和一页一题目标冲突。
- `QuestionField.tsx` 已有原生表单语义，但客户端显示 0—4 分值且视觉仍是传统问卷卡片。
- `questionnaire.ts` 完整保存 55 道医学问题，适合继续作为评分语义来源，但个人信息和若干开放题需要医院版新模型。
- `assessment.ts` 的八维结果和红旗逻辑已测试，应保持规则含义不变。
- `submission.ts`、`submitSurvey` 云函数和五集合存储已形成稳定链路，应通过归一化层兼容新旧答案，而不是重写存储。
- 医院版与诺玛元一版共用代码但有独立品牌、路径、版本和草稿键；本轮只替换医院版体验，诺玛元一继续运行旧流程。
- 云环境存在历史企业微信通知函数，但当前 `submitSurvey` 没有调用它们，且历史函数面向其他品牌。医院版需要在当前提交函数中增加独立、失败不阻断提交的通知适配。

## 方案选择

### 采用：医院版新流程与旧流程并存

`App` 根据品牌分流：医院版进入新的移动端问卷应用；诺玛元一继续使用现有 legacy 应用。医院版使用新的配置化页面模型，后台提交服务同时接受新医院答案、旧医院答案和诺玛元一答案。

该方案比直接改写共享问卷风险更低：线上滚动部署期间，旧静态页面仍可向新云函数提交；诺玛元一不会被医院版的手机号、条件题和导航变化影响。

## 信息架构

医院版按十个模块组织，但进度不显示总题数：

1. 基本信息：姓名、完整手机号，日期自动生成。
2. 当前关注与整体状态：优先关注、半年变化、Q1—Q3。
3. 精力与恢复：Q4—Q8。
4. 睡眠与日间状态：Q9—Q14。
5. 压力与认知：Q15—Q19。
6. 胃肠与排便：Q20—Q25及食物条件题。
7. 代谢与体重：Q26—Q29。
8. 心肺、运动与肌肉：Q30—Q34。
9. 男性活力与排尿：Q35—Q40。
10. 生活方式与医学安全：职业状态、Q41—Q55、行为目标和最终优先目标。

模块过渡页不参与答案校验，可点击继续；普通单选选中后保留约 190ms 反馈再进入下一题。文本、手机号、多选、医学安全题、Q55和最后提交保留明确按钮。

## 配置化分支

- Q25 为 3 或 4 时显示 `q25Foods` 多选；修改为其他答案后自动移除该条件答案。
- Q44 不为 0 时显示 `q44DrinkType` 单选。
- Q48 包含抗生素（0）时显示 `q48AntibioticWhen` 单选。
- Q47 的“上述食物平时都比较少”和其余食物互斥。
- Q48 的“均无”和其余产品互斥。
- 最终优先改善题从 `topConcerns` 动态生成选项。
- Q35—Q37允许“暂不回答”，服务端保存为 `value: null` 和 `answered: false`，不参与风险分值。

条件由题目定义中的 `visibleWhen`、`exclusiveOption` 和 `optionsFromAnswerId` 描述；导航只遍历当前可见页面，不在组件中散落题号判断。

## 数据兼容

- 新增 `phone` 完整手机号；继续派生并保存 `phoneLast4`，管理接口同时兼容两者。
- `age` 在新医院提交中保存为 `null`，旧提交继续接受数字年龄。
- 自动写入 `date: YYYY-MM-DD`。
- 删除的旧开放字段继续写入空字符串：`workStatusOther`、`topConcernsOther`、`q25Food`、`q44Drink`、`q48Details`、`twelveWeekGoalsOther`。
- Q47 客户端保存所选食物，服务端生成兼容旧评分的 `q47` 以及原始 `q47Foods`。
- 条件题原始答案使用独立字段保存，不改变 Q1—Q55 的既有医学含义。
- 新旧医院负载通过 `phone` / `phoneLast4` 识别并分别校验，问卷版本字符串保持兼容。

## 视觉与组件

新建独立 `tokens.css` 管理白色、青绿色、橙色安全态、间距、圆角、字体、阴影和动效。医院版不使用大面积渐变、毛玻璃或巨型卡片。

组件边界：

- `HospitalSurveyApp`：阶段、答案、导航、保存和提交编排。
- `SurveyShell`、`SurveyHeader`、`ProgressBar`：480px移动端框架和十段进度。
- `WelcomePage`、`ResumePage`、`ModuleIntro`、`CompletionPage`：流程页面。
- `QuestionPage`：问题标题、说明、错误和底部安全区。
- `SingleChoice`、`MultiChoice`、`IdentityInput`：可访问的原生输入组件。

所有选项只显示自然语言。选中态使用青绿背景、边框和 Check 图标，普通答案不使用风险色。医学安全模块顶部切换为橙色，但“是/否”选中态保持一致。

## 自动保存与导航

医院版使用独立草稿键，保存当前页面 ID、答案和更新时间。检测到有效草稿时首页显示“继续填写 / 重新开始”。刷新和返回保留答案；修改上游答案后会重新计算可见页面并清除已失效分支答案。提交成功后清除草稿。

## 完成页

完成页只展示“健康信息采集完成”、五类采集清单和“问卷 → 微生态检测 → 综合健康报告”流程，不把八维评估细节或医学计算暴露给客户。红旗触发时只显示温和橙色人工确认提示。

## 验证

- 单元测试覆盖页面序列、条件分支、互斥选择、动态最终目标、手机号校验、新旧负载归一化、敏感题跳过、红旗和通知文案。
- 组件测试覆盖首页、恢复/重开、单选自动前进、多选确认、返回修改、Q55确认和完成页。
- 浏览器在 375、390、430、1440 四种宽度验证首页、输入、单选、多选、各条件分支、男性活力、医学安全、完成页、安全区和控制台错误。
- 使用虚构数据完成 CloudBase 五表和企业微信测试；测试记录按精确 ID 清理。

## 非目标

- 不增加 Bristol 1—7 问题。
- 不修改既有医学问题含义和评分阈值。
- 不制作后台管理界面。
- 不迁移或重写历史数据。
