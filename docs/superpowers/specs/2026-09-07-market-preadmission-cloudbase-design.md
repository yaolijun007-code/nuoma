# 市场预住院 CloudBase 系统设计

**日期：** 2026-09-07  
**状态：** 已确认，进入实施  
**目标用户：** 建始民族医院市场人员与系统管理员

## 1. 建设目标

在现有 CloudBase 项目中增加一套需要登录的内部市场工作台。市场人员能够用姓名、手机号或住院号查找患者，核对其住院次数、主要诊断和每次住院起止时间，随后登记患者类型、拟住院日期、拟住院科室、主要问题与联系结果。登记保存成功后，云函数向指定企业微信群发送一条预住院提醒。

本版本只解决“查历史—登记—推送—追踪状态”这一条主流程，不建设完整 CRM，不包含收费、医保、地址、家庭成员、病历原文或临床诊断决策。

## 2. 已确认的业务规则

1. 系统仅供内部账号登录后使用，匿名用户不得搜索、查看或登记患者数据。
2. 搜索结果不能仅凭姓名自动认定为同一患者。姓名重复、手机号重复、住院号冲突或身份风险记录必须提示市场人员人工核对。
3. 患者详情只展示：姓名、性别、年龄、主要联系电话、住院号、住院次数、诊断统计以及各次住院的入院日期、出院日期、科室和主要诊断。
4. 预住院登记至少包括：患者类型、计划住院日期、拟住院科室、主要问题、联系结果；患者姓名和联系方式从患者档案带入，允许在登记时核对和修正本次联系电话，但不回写历史主档。
5. 先持久化登记记录，再尝试群通知。群通知失败不回滚登记；页面明确显示“推送失败”，并允许有权限人员重试。
6. 同一个 `clientSubmissionId` 只创建一条登记记录。已经推送成功的记录不得因重复点击再次推送。
7. 按用户明确要求，企业微信群消息包含患者完整姓名和完整联系电话。群消息不包含详细住院史、全部诊断、费用、住址或其他无关健康信息。
8. 群消息把记录标记为“预住院线索，待医务人员确认”，不得表述为已经安排床位、已经确诊或已经收治。
9. 查询、查看详情、创建登记、通知发送结果与重试均写入审计日志。
10. 查不到历史记录的新患者可填写姓名、联系方式和可选的性别/年龄，建立零住院史档案后继续预住院登记；新档案不与同名或同手机号患者自动合并。

## 3. 用户与权限

### 市场人员

- 账号命名使用简短规则，例如 `sc001`、`sc002`，兼顾 CloudBase 用户名最小长度并便于记忆。
- 密码不得与账号相同；由管理员初始化强密码并线下交付，后续应要求更换。
- 可搜索患者、查看有限历史、创建预住院登记、查看本人登记和通知状态。
- 只能重试本人创建且通知状态为失败的登记。

### 管理员

- 具备市场人员全部权限。
- 可查看全部登记、管理账号与角色、执行患者数据导入、重试失败通知。

权限以 CloudBase 登录 UID 和 `hospital_market_users` 角色记录共同判定。数据库客户端直连权限默认全部拒绝，所有业务数据只能经过 `marketPreadmission` 云函数访问。

## 4. 信息架构与界面

页面使用顶部轻量导航，不设置复杂侧栏和指标大屏。默认入口直接落到患者搜索。

### 登录页

- 医院名称、系统名称、账号、密码、登录按钮。
- 一句隐私提示：仅限授权人员处理工作所需信息。
- 错误提示使用 `aria-live`，不暴露账号是否存在。

### 主工作台

顶部固定显示三步流程：`1 查患者 → 2 看历史 → 3 登记推送`。

搜索区只保留一个输入框，支持姓名、手机号、住院号；结果卡片显示足够区分患者的信息和身份风险提示。用户选定患者后进入详情，不自动选择同名记录。

搜索区同时提供醒目的琥珀色“新患者首次登记”提示卡。新患者只采集本次业务必需的姓名、联系方式和可选性别/年龄，提交预住院时以幂等标识建立可再次查询的零住院史档案。

患者详情上部为精简身份卡，下部为按时间倒序的住院记录表；手机窄屏改为纵向卡片。诊断统计与住院时间使用明确字段名，不把缺失出院日期推断为仍在住院。

预住院表单与患者详情同页衔接，减少跳转。提交按钮文案为“保存并推送到企业微信群”，提交中禁止重复点击。

提交后展示登记编号和三种状态之一：

- 已推送：绿色确认，可开始下一位患者。
- 推送失败：登记已保存，显示可操作的重试按钮。
- 未配置：登记已保存，提示联系管理员配置群机器人。

“我的登记”使用简表展示登记编号、患者姓名、计划日期、创建时间和通知状态，可进入详情或重试。

### 视觉与可访问性

- 白色、冷灰与医院青绿色为主，琥珀色用于身份风险，红色只用于失败。
- 使用系统中文字体、清晰边框和轻微色块，不依赖大面积阴影或装饰性渐变。
- 正文最小 14px，表单控件与触控目标不小于 44px。
- 所有输入有可见标签；键盘焦点清晰；状态与错误可被读屏软件感知。

## 5. 数据模型

### `hospital_market_users`

`uid`、`username`、`displayName`、`role` (`market`/`admin`)、`active`、`createdAt`、`updatedAt`。

### `hospital_patients`

`patientId`、`patientCode`、`name`、`sex`、`age`、`phone`、`hospitalNo`、`admissionCount`、`identityRisk`、`source`、`updatedAt`。历史导入标记原来源；市场首次登记标记 `market_new`。建立姓名、标准化手机号、住院号和患者 ID 查询索引。

### `hospital_encounters`

`encounterId`、`patientId`、`admissionDate`、`dischargeDate`、`department`、`mainDiagnosis`、`sequence`。

### `hospital_diagnosis_stats`

`patientId`、`diagnosis`、`count`、`lastAdmissionDate`。

### `hospital_preadmissions`

`recordId`、`clientSubmissionId`、`patientId`、`patientSnapshot`、`contactPhone`、`patientType`、`plannedAdmissionDate`、`intendedDepartment`、`mainProblem`、`contactResult`、`notes`、`createdByUid`、`createdByName`、`createdAt`、`updatedAt`、`notificationStatus` (`pending`/`sending`/`sent`/`failed`/`not_configured`/`delivery_unknown`)、`notificationAttempts`、`lastNotificationAt`、`lastNotificationErrorCode`。`patientType` 只允许城镇职工医保、低保人员医保、普通居民医保、特困供养人员医保、自费；`intendedDepartment` 只允许风湿免疫科、康复科、老年医学科、住院内一科、住院外一科。

### `hospital_preadmission_notification_logs`

`recordId`、`attempt`、`status`、`responseCode`、`errorCode`、`createdAt`。不得记录机器人地址或患者消息正文。

### `hospital_market_audit_logs`

`uid`、`action`、`targetType`、`targetId`、`result`、`createdAt`、`requestId`。搜索条件只记录类型和哈希/末四位等必要线索，不记录完整手机号。

## 6. 云函数接口

单一云函数 `marketPreadmission` 接收 JSON 请求：

- `getSession`：返回登录用户显示名与角色。
- `searchPatients`：姓名、手机号或住院号精确/前缀查询，最多 20 条。
- `getPatientHistory`：返回选定患者的有限身份、诊断统计和住院列表。
- `createPreadmission`：校验输入、幂等创建记录、尝试群通知并返回通知状态。
- `listPreadmissions`：市场人员只返回本人记录，管理员可按权限查看全部。
- `retryNotification`：仅对未成功的记录重试，成功记录直接返回原状态。

错误响应使用稳定代码，如 `AUTH_REQUIRED`、`FORBIDDEN`、`INVALID_INPUT`、`PATIENT_NOT_FOUND`、`NOTIFICATION_FAILED`，前端根据代码给出中文操作提示。

## 7. 企业微信群通知

机器人地址仅保存在云函数环境变量 `JSMZ_PREADMISSION_WECOM_WEBHOOK_URL`，不提交到 Git、不写入前端、不写日志。发送前校验 HTTPS、企业微信域名、固定接口路径和非空 key。

消息字段：预住院登记标题、登记编号、患者完整姓名、完整联系电话、性别/年龄、住院次数、最近一次住院时间、患者类型、计划住院日期、拟住院科室、主要问题、联系结果、登记人、登记时间、待确认状态。

所有可编辑文本移除换行和 Markdown 控制字符并限制长度。网络请求设置超时，企业微信返回非零 `errcode` 时记为失败。日志只保留错误代码和发送状态。

## 8. 历史数据迁移

源 SQLite 数据库只读。导出脚本仅抽取本系统所需字段，输出患者、住院记录和诊断统计三份 JSONL，以及包含记录数、字段完整性、重复标识和 SHA-256 的清单。

导入前验证患者 ID 唯一、住院记录外键有效、日期格式有效；遇到同名、重复手机号或住院号冲突时保留原患者 ID，并设置 `identityRisk`，不得自动合并。真实数据文件不提交 Git。

## 9. 安全与运维

- CloudBase 静态托管使用 HTTPS；页面不在 `localStorage` 持久化患者详情或表单内容。
- API 响应设置 `no-store`；退出登录时清空内存状态。
- 数据库规则拒绝网页客户端直接读写业务集合。
- 所有密钥只记录环境变量名和是否配置，不在诊断输出中显示值。
- 真实群测试只能使用合成患者信息，因为机器人消息发送后无法撤回。
- 部署验收包括：未登录访问、角色越权、同名患者核对、幂等重复提交、通知失败重试、真实群合成消息、移动端和键盘操作。

## 10. 验收标准

1. 未登录用户无法取得任何患者或登记数据。
2. 市场账号能在 3 个主要步骤内完成患者选择和预住院登记。
3. 患者详情准确显示住院次数、主要诊断和每次住院时间，缺失值原样标注。
4. 同名或身份风险患者不会被系统自动合并或自动选中。
5. 有效登记先保存，再推送包含完整姓名与完整联系电话的群消息。
6. 重复提交不会创建重复记录或重复发送成功消息。
7. 通知失败时登记仍可查询，并可安全重试。
8. 前端产物和源码中不包含机器人地址、密码或真实患者导出数据。
9. 自动化测试、TypeScript 类型检查、所有构建和敏感信息扫描通过。
